# Knowledge base

Reforge decides from recorded facts, never from guesses. This page lists where
each fact comes from and how to refresh it.

## Flutter releases

`packages/reforge_core/lib/src/knowledge/data/flutter_releases.g.dart` is
generated by `tool/generate_flutter_knowledge.dart` for every stable release
since 3.0.0. Older stable releases (1.17.0 to 2.10.5) are recorded only by
version and framework revision, from the release manifest, so that the
`.metadata` of an old app identifies the SDK that created it; plans and
findings use no facts about those releases.

| Fact | Source at each release tag |
| --- | --- |
| Version, framework revision, Dart version, release date | Flutter release manifest (`releases_macos.json`) |
| Gradle, AGP, Kotlin, Java and minSdk error and warning floors | `DependencyVersionChecker.kt` (3.32+), `dependency_version_checker.gradle.kts` (3.22 to 3.29); no floors before 3.22 |
| Template Gradle, AGP and Kotlin versions | `lib/src/android/gradle_utils.dart` |
| Default compileSdk, targetSdk, minSdk and NDK | `FlutterExtension.kt`, `flutter.groovy` or `flutter.gradle` |
| Template DSL, declarative plugins, namespace | App templates |
| Template `gradle.properties` (JVM arguments, Jetifier, AGP 9 opt-outs) | `templates/app_shared/android.tmpl/gradle.properties.tmpl` (before 3.29), `templates/app/android.tmpl/gradle.properties.tmpl` |
| Imperative Gradle apply support | `packages/flutter_tools/gradle/flutter.gradle` (deprecation and removal messages) |
| Minimum iOS deployment target | `darwin.dart`, `ios_deployment_target_migration.dart` or `deployment_target_migration.dart` |
| Minimum macOS deployment target | `darwin.dart`, `macos_deployment_target_migration.dart` (3.7+) or the app template's `project.pbxproj` |
| Required and recommended Xcode; minimum and recommended CocoaPods | `lib/src/macos/xcode.dart`, `lib/src/macos/cocoapods.dart` |
| compileSdk the Android embedding requires (3.29+) | `engine/src/flutter/tools/androidx/files.json`, and `minCompileSdk` in the AAR metadata of each listed AndroidX library |
| Android project migrations run before every Gradle build | The `<ProjectMigrator>[...]` list in `lib/src/android/gradle.dart` |
| Whether Flutter applies the Kotlin Gradle plugin itself, and whether the app template applies it | `FlutterPluginUtils.kt`; app template build script |

Refresh:

```bash
curl -o /tmp/releases_macos.json \
  https://storage.googleapis.com/flutter_infra_release/releases/releases_macos.json
cd packages/reforge_core
dart run tool/new_flutter_releases.dart --manifest /tmp/releases_macos.json
dart run tool/generate_flutter_knowledge.dart --flutter <flutter checkout with tags> \
  --manifest /tmp/releases_macos.json [--gradle-cache ~/.gradle/caches/modules-2/files-2.1] \
  [--download-aars]
```

`new_flutter_releases.dart` lists the stable releases the knowledge base does
not describe yet. The compileSdk the Android embedding requires comes from the
AAR metadata of its AndroidX libraries, read from the Gradle module cache.
Building any app with a release puts them there; otherwise `--download-aars`
fetches them from Google's Maven repository, and without it the generator
lists the missing AARs. The output is rewritten only when the knowledge
changed.

The generator reports every value it cannot extract. Review the diff; the
tests in `test/knowledge/knowledge_base_test.dart` pin values verified by hand.

## Keeping the knowledge current

The knowledge base is part of each Reforge build, so newer Flutter releases
need a newer Reforge. `.github/workflows/update-knowledge.yml` checks the
release manifest every week; when a stable release appears that the knowledge
base does not describe, it regenerates the Flutter and toolchain knowledge and
opens a pull request (see [releasing.md](releasing.md)).

Users are told when their copy is behind: `reforge --version` and `reforge env`
show the knowledge base date, `plan --to stable` names the release it resolved
to and warns after 90 days, and a Flutter version newer than the knowledge base
is reported as `REFORGE_KNOWLEDGE_OUTDATED`.

## Toolchain releases

`toolchain_releases.g.dart` is generated by
`tool/generate_toolchain_releases.dart`:

| Fact | Source |
| --- | --- |
| Stable Gradle releases and distribution SHA-256 checksums | services.gradle.org |
| Stable Android Gradle Plugin releases | Google Maven metadata |
| Stable Kotlin Gradle plugin releases | Maven Central metadata |

Recipes only select versions from these lists.

## Facts, observations, inferences

Every piece of evidence Reforge reports has a kind:

- `knowledge`: a documented fact with a source URL;
- `projectFile` / `generatedFile`: observed in the repository;
- `environment`: observed on this machine;
- `inference`: derived by Reforge from other evidence.

Confidence follows from the kinds involved: literal values in files are
certain, values resolved through variables or generated files are high,
heuristics such as JDK discovery are medium.

Future compatibility observations (from CI runs building packages against
toolchain matrices) will be a separate kind with run identifiers, toolchain
versions and timestamps, so a verified observation is never confused with a
documented requirement.
